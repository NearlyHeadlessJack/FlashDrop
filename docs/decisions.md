# 技术决策记录（ADR 摘要）

这里记录“为什么这样实现”，以及接受了哪些代价。实现本身见 [architecture.md](architecture.md)，线协议见 [protocol.md](protocol.md)。

---

## ADR-001：只用 Python 标准库

**背景**：用户需要一个能直接运行的双机文件快传工具，不希望安装 Node/Python 依赖或构建前端。

**决定**：后端 HTTP 服务、P2P 协议、UI 静态文件、原生选择器全部用标准库 + 原生 Web 技术。发行包仅包含 Python 源码和静态资源。

**结果**：
- 优点：部署简单；无需网络安装依赖；易于审计；离线可用。
- 代价：HTTP/API 框架功能较少；没有现成的 WebSocket、认证；测试/打包需要自行维护。
- 边界：除非有明确收益，不引入 Flask/FastAPI/uvicorn/React 等运行时。引入时必须更新 `pyproject.toml`、打包、部署文档和验证流程。

## ADR-002：自建 TCP 协议，而不是 HTTP 上传或 SFTP

**背景**：文件总量可能非常大，HTTP multipart 需要浏览器把文件上传给本地后端（或单独建服务），难以做多端口并行、块级续传和自定义进度。SFTP 需要额外服务端/认证配置，且多通道和 WebUI 集成成本高。

**决定**：
- 发送端监听；
- 一条 TCP 控制连接承载 JSON；
- 多条 TCP 数据连接承载固定头 + 原始块；
- 自定义 resume、进度、完成语义。

**结果**：
- 优点：零拷贝式局域网传输路径清晰；多通道调度可控；易于把每块 CRC 和续传状态做进协议。
- 代价：需要自己处理帧边界、心跳、半关闭、取消和错误传播；不能直接复用 HTTP/2 的多路复用与 TLS。
- 后续：如果扩展公网，优先在 TCP 外包裹 TLS 并增加身份认证，而不是直接暴露当前协议。

## ADR-003：发送方监听，接收方主动连接

**背景**：发送端需要事先把“我要发的文件”准备好，并在 UI 上显示可分享的地址/端口；接收方需要先看到清单再决定保存位置。

**决定**：发送端 `0.0.0.0` 监听控制 + 数据端口，接收方连接控制端口，控制消息里拿到数据端口后再主动连数据端口。

**结果**：
- 优点：发送端无需知道接收方地址；符合“开启传输→分享地址”的交互。
- 代价：发送端必须处理防火墙入站；数据的 TCP 方向也是接收方→发送方（数据发送端 send，接收端 recv，逻辑方向不受影响）。
- 非安全设计：不校验谁可以连接；任何 LAN 客户端都能成为接收方。

## ADR-004：多 TCP 数据连接 + 有界在途窗口

**背景**：单条 TCP 在局域网/高 RTT 下可能无法跑满带宽；用户明确要求多端口提高效率。

**决定**：
- 1–8 条独立数据 socket；
- 块大小 4 MiB（协议上限 32 MiB）；
- 全局游标动态分配块，而不是按文件静态绑定连接；
- 限制 `window = max(conn, min(64, conn*4))` 个在途块。

**结果**：
- 优点：单文件也能多连接并行；小文件按序交付；窗口限制限制了接收端乱序内存。
- 代价：接收端必须能处理乱序并带 pending 缓冲；连接不均衡时窗口会限制最快连接。
- 备选：按文件绑定连接对单个大文件无效；无窗口会在慢链路下造成内存风险；每块应用层 ACK 会明显增加控制开销。

## ADR-005：控制端口 + 动态数据端口

**背景**：多数据端口的数量/可用性随机器变化；逐个固定端口不现实。用户要求“其他传输端口的信息通过信息传输端口提供”。

**决定**：发送端绑定一个控制端口，然后扫描空闲端口绑定 N 个数据端口；`welcome` 返回端口列表；接收端使用控制连接的同一个 IP 去连数据端口。

**结果**：
- 优点：可配置连接数；端口冲突自动跳过；无需用户手工管理 N 个端口。
- 代价：防火墙必须放行动态端口（建议按程序放行）；端口可能不连续。
- 注意：控制连接的对端 IP 用于数据连接，避免 DNS 多地址不一致。

## ADR-006：断点续传用采样快速指纹，而非全文件哈希

**背景**：用户要求续传，但大文件在开始前完整哈希会额外读一遍磁盘，延迟启动；许多文件也无法快速。

**决定**：
- 续传必须同时匹配 `file_id/path/size/mtime_ns/quick_hash`；
- 路径在线协议中统一为 NFC、只用 `/` 分隔，file id 由 NFC casefold 路径派生；
- quick_hash 采样头尾各最多 64 KiB；
- 每个数据块 CRC32 + 最终精确大小；
- 不做全文件 SHA-256。

**结果**：
- 优点：启动快；普通编辑/截断能识别；中断恢复开销低。
- 代价：无法保证“任意伪造/极端碰撞”下的内容身份；不是安全校验。
- 后续：如果增加全文件哈希，需要在协议中支持 prefix/Merkle 或接受续传后重读完整文件；不能只在 ready 里加一个不可续的 hash。

## ADR-007：接收端连续写入 + 乱序缓冲

**背景**：多连接意味着块可能乱序到达；如果直接按 offset 散写，崩溃后无法知道哪些字节是连续有效的，续传 offset 不可靠。

**决定**：
- 每个文件只提交连续前缀；
- 乱序块暂存 pending；
- `.part` 文件长度就是安全续传点；
- 文件大小写满后关闭句柄，避免文件描述符耗尽；
- 完成时 fsync + `os.replace`。

**结果**：
- 优点：续传语义简单可靠；数据库/文件系统崩溃后仍能通过长度恢复。
- 代价：需要一个乱序窗口和内存缓冲；慢连接可能造成阻塞。
- 保护：发送端窗口 + 接收端 `MAX_PENDING_CHUNKS`，越界直接失败而不是无界占用。

## ADR-008：逐文件异步完成确认

**背景**：多文件传输中，所有文件都等最后才落盘会导致已完成的巨大文件也暴露在失败风险中；全有或全无恢复成本高。

**决定**：
- 文件独立完成并原子替换；
- 文件完成后写 `status=done` 侧面记录；
- 整次会话成功才清理所有状态；
- 失败时保留 done 记录和未完成 part，下次跳过 done 文件。

**结果**：
- 优点：失败后不用重传完整的大文件；用户体验更好。
- 代价：一次失败可能让最终目录处于“部分新、部分旧”的状态；UI 必须显示失败，让用户知道不是全量成功。
- 不做“整目录事务”；跨文件事务需求超出文件快传语义。

## ADR-009：原生选择器在独立子进程中运行

**背景**：本机路径只有原生文件对话框能可靠获得；浏览器 `<input type=file>` 不能给出路径，且会把大文件读进浏览器。Tk 对主线程/平台有要求，在 HTTP 服务线程中创建窗口容易出问题。macOS 常见的 Homebrew Python 还可能没有 Tk。

**决定**：
- 每次选择启动 `python flashdrop/picker.py --kind ...`，子进程输出 JSON；父进程读取。
- macOS 在子进程里优先调用系统 `/usr/bin/osascript` 的 JXA Standard Additions（Finder 风格窗口），失败才回退 Tk。
- Windows/Linux 直接使用 Tk。

**结果**：
- 优点：WebUI 本机交互与真正的路径直传兼得；窗口/服务线程隔离；macOS 不依赖 Tk；支持多文件选择。
- 代价：多一条 osascript/Apple Events 依赖链；沙箱化或禁用自动化的环境可能拒绝，需要 Tk/手动路径后备。
- 安全：路径来自本机用户选择，不经过浏览器上传。

## ADR-010：Windows 接收端在本地适配 macOS 文件名

**背景**：macOS 允许 Windows 非法字符、保留设备名、尾部空格/点和更长的组件。如果发送端直接照搬，传输会在最终落盘时才失败，浪费大量已传字节。

**决定**：
- 线协议保留源清单路径，文件 ID 和续传身份不随目标 OS 改变；
- 接收端是 Windows 时，在收到清单后由 `naming.plan_destinations` 生成确定性的 `dest_rel`；
- 非法字符替换、保留名避让、尾部空白点清理、过长组件截短，并给变化项加稳定短哈希；
- 目标路径冲突直接拒绝开始，绝不覆盖；
- 接收端 UI 展示实际保存名和适配示例。

**结果**：
- 优点：Mac→Windows 的常见文件无需手动改名；清单阶段即可预知目标名；续传仍使用源路径身份。
- 代价：部分文件名会变化，发送端 UI 看不到 Windows 适配后的名字；用户需要看接收端清单。
- 非目标平台的接收端不做适配，保持原样。

## ADR-011：POSIX 权限只保留 rwx

**背景**：macOS → macOS 传脚本/工具时，如果完全不保留权限，可执行文件会变成不可执行；但 setuid/setgid/sticky 不适合一个无认证的传输工具。

**决定**：
- POSIX 发送端在 manifest 附带 `mode`，仅 `0o777` rwx 位；
- POSIX 接收端在原子落盘后 `chmod`；
- Windows 发送/接收均忽略；
- ACL、所有者、xattr、资源叉不处理。

**结果**：
- 优点：脚本、可执行文件和部分工具链文件在 POSIX 两端保留执行语义；协议向后兼容。
- 代价：元数据恢复不完整；`.app`/Framework 仍应打包；不能通过该字段复制特权位。

## ADR-012：WebUI 使用轮询而不是 WebSocket

**背景**：这是一个本机单用户控制台，状态更新频率低；标准库没有 WebSocket 服务端。

**决定**：前端轮询 `/api/state`（650–2600 ms），文件列表按 revision 分页拉取。

**结果**：
- 优点：实现简单、断线自动恢复、无额外协议。
- 代价：不是逐帧实时；高频更新有轮询开销。
- 可接受原因：文件传输在后台线程；浏览器的进度显示只需要约 1 秒级刷新。状态 payload 已裁剪为统计而非完整文件列表。

## ADR-013：线程 + 阻塞 socket，而非 asyncio

**背景**：传输本质上是大量阻塞读写，标准库 HTTP server 是线程模型；文件系统调用也是阻塞的。

**决定**：HTTP 请求线程、服务线程、控制 reader、数据 worker、finalize 线程显式管理，socket 设超时，通过关闭 socket 打断阻塞。

**结果**：
- 优点：与标准库 HTTP 服务一致；数据 worker 代码直观；可以并行发送/接收。
- 代价：需要小心线程收尾、锁顺序、回调执行上下文；调试复杂于 asyncio。
- 后续：如果引入 TLS/大量并发会话，需重新评估 asyncio 或进程隔离。

---

## ADR-014：当前不做加密/认证

**背景**：用户明确表示“暂时不需要考虑安全性”，首要是可靠与速度。

**决定**：不实现 TLS、登录、共享密钥或签名；`data_token` 只用于数据 socket 与错误连接串线。WebUI 限定回环地址。

**结果**：
- 优点：实现简单、性能开销低、无需证书分发。
- 明确风险：任何能访问控制端口的 LAN 客户端都可以尝试连接、查看清单并接收。
- 必须遵守：文档和 UI 明确提示“只用于可信局域网”；不要把端口暴露到公网；不把这一状态误解为“端到端安全”。

## 未来升级优先级

1. **可选 TLS + 一次性配对码**：在不改变块调度的前提下包一层安全连接，升级协议版本。
2. **全文件内容哈希**：引入可续传的哈希设计（分块/Merkle 或完成时全量校验），并保留快速指纹用于早期 resume 判断。
3. **多接收方/广播**：需要重构 SendService 生命周期、每会话 token、数据端口复用与 UI 会话列表。
4. **可恢复目录状态索引**：用追加日志或数据库替代每文件 JSON，改善十万级文件性能。
5. **带宽限速与优先级**：在 worker socket 写入前加令牌桶，并与窗口调度协同。
6. **可选的增量/同步模式**：目前只发送清单中的全部文件（续传除外），不做 mtime 差异同步。
7. **macOS 实机验收与 CI**：在真实 macOS 上跑 osascript 选择器、Safari、POSIX 权限和长时间续传；当前只在 Windows 环境验证了跨平台纯逻辑。
8. **完整元数据**：符号链接、扩展属性/资源叉、ACL 需要协议版本升级和安全的恢复策略，不适合直接塞进当前 manifest。
